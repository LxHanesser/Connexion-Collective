11 月 3 日，俄罗斯主机商 Beget 发布通告，承认遭遇了一次破坏性攻击。据其说明与多家俄语技术媒体报道，攻击者获取了管理面的访问权限，随后运行擦除脚本，导致部分云服务数据丢失，**部分备份也未能幸免**。

这类事件比勒索软件更彻底：勒索至少还留着数据等你付钱，擦除脚本连谈判的机会都不给。

## 一、攻击链里最值得注意的一环

从公开信息看，攻击者的路径大致是：

```
管理面凭据/权限 → 批量操作 → 删除生产数据 → 波及备份
```

真正致命的不是「数据被删」，而是**备份和管理面在同一个信任域里**。如果备份账号、备份存储、备份控制台和生產环境共用一套凭据，那么攻击者拿到一次权限，就能同时毁掉数据和退路。

这也是很多「3-2-1 备份」实施里的常见漏洞：三份副本、两种介质、一份异地 —— 听起来很完整，但三份副本的删除权限是同一套，等于只有一份。

## 二、备份应该怎么设计

行业里这几年更常提的是 **3-2-1-1-0**：

| 数字 | 含义 |
|---|---|
| 3 | 至少三份副本 |
| 2 | 两种不同介质 |
| 1 | 一份异地 |
| 1 | 一份离线或不可变 |
| 0 | 恢复演练零错误 |

其中最难做到、也最关键的是「1」：**离线或不可变**。

具体到实现：

- 对象存储开**版本控制**与**对象锁**（WORM），删除需要单独的、不常用的权限；
- 备份写入用**独立账号**，与生产账号没有共同的 SSO、没有共同的恢复邮箱；
- 关键备份定期**离线导出**（磁带、冷存储、物理硬盘），断网保存；
- 备份控制台的管理员账号单独开 2FA，且不与生产管理员复用。

## 三、恢复演练比备份本身更重要

很多团队有备份，但从来没在真实故障里恢复过。真出事时才发现：

- 备份是完整的，但恢复脚本依赖一个已经被删的服务；
- 备份有加密，但密钥存在同一台被删的机器上；
- 备份能恢复，但恢复要 40 小时，业务等不了。

所以「0」不是口号：每季度至少做一次**从备份到可用服务**的完整演练，记录恢复时间（RTO）和数据丢失窗口（RPO）。演练失败的备份，等于没有备份。

## 四、对个人站点的启示

个人站点没有主机商那么复杂，但逻辑一样：

1. 代码和文章放 git，远端不要只有一个（GitHub + 本地 + 镜像）。
2. 图片等媒体放对象存储，开启版本控制，重要文件本地留一份。
3. 不要把「唯一备份」放在与站点同一个账号下 —— 账号被盗时会被一锅端。
4. 定期验证：随便挑一个文件，从备份恢复一次，确认真的能用。

## 五、结尾

Beget 这次事件的细节还在陆续披露，但教训已经足够清楚：**备份的安全性不取决于副本数量，而取决于删除权限是否被隔离。**

当攻击者能用一个账号删掉生产和备份时，你有多少份副本都不重要。
