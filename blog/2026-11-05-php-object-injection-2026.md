十月的 NVD 里躺着两个不太起眼的条目：`CVE-2026-97284`（Icegram ≤ 3.1.31，CVSS 8.8）和 `CVE-2026-94390`（Hide Shipping Method for WooCommerce ≤ 1.5.4，CVSS 7.2）。都是 PHP 对象注入。

每次看到这类漏洞，评论区总有人说「PHP 反序列化是老黄历了」。但 WordPress 插件生态每年都在重复同一个错误：把用户提交的字符串丢进 `unserialize()`，然后期待里面的类刚好都安全。

这篇文章不讨论怎么打，只讨论为什么这类问题反复出现，以及作为站点运营者能做什么。

## 一、对象注入到底注入的是什么

PHP 的 `serialize()` 把对象写成字符串，`unserialize()` 再把它还原。问题出在还原过程：如果字符串来自用户，攻击者就能指定「还原成哪个类」，而 PHP 在还原时会自动调用一些魔术方法，比如 `__wakeup()`、`__destruct()`。

单个类通常做不了什么。但如果站点里装了足够多的插件，这些类的方法可以像积木一样拼起来：A 类的 `__destruct` 调用 B 类的方法，B 类的方法又调用 C 类的文件写入 —— 这就是所谓的 POP chain（Property-Oriented Programming）。

所以对象注入的严重程度不取决于漏洞本身，而取决于**目标站点装了哪些插件**。同一个 payload，在插件少的站上可能只是报错，在插件多的站上就是 RCE。

## 二、为什么 WordPress 插件是高发区

三个原因叠在一起：

1. **入口多**。文章、评论、用户资料、订单备注，任何能存字符串的地方都可能成为反序列化入口。
2. **权限模型**。Contributor 能写草稿，Editor 能发布和改设置。很多插件把「Contributor 可提交的数据」当成可信数据。
3. **更新慢**。插件作者发版、用户升级、主机商缓存，中间任何一个环节卡住，漏洞窗口就被拉长。

这次两个 CVE 都需要 Contributor 或 Editor 权限，单看不算「未授权 RCE」。但现实中账号泄露、弱口令、被撞库的编辑账号比比皆是，门槛没有 CVSS 看起来那么高。

## 三、防御不是「装个 WAF」

对象注入的 payload 通常是序列化字符串，可能被 base64、gzip 或自定义编码包一层。WAF 规则很难在不误伤正常流量的前提下稳定识别。

真正有效的是三件事：

**第一，不要对用户输入调 `unserialize()`。** 新代码用 `json_decode()`，它不会实例化对象。这是最彻底的做法。

**第二，必须用时关掉类实例化。** PHP 7 以后 `unserialize($data, ['allowed_classes' => false])` 可以只还原数组和标量，不创建任何对象。很多老代码不知道这个参数。

**第三，减少插件数量。** 每多一个插件，就多一批可被串进 gadget chain 的类。一个只用一个插件的站，和一个装了三十个插件的站，面对同一个漏洞的风险完全不同。

补充两条工程习惯：

- 给编辑账号开 2FA，Contributor 账号按需分配，不用就删。
- 监控 PHP 错误日志里突然增多的 `unserialize()` 警告和 500，对象注入在成功前往往会留下痕迹。

## 四、一点个人看法

PHP 的对象注入和 Java 的反序列化是同一类问题：语言给了「把字符串还原成对象」的能力，框架又给了对象太多自动执行的机会。只要这两件事同时存在，漏洞就会周期性出现。

对个人站点来说，最现实的策略不是「研究怎么防住每一个 payload」，而是**把攻击面缩到最小**：少装插件、及时更新、权限收紧。这三件事的收益，远比在 WAF 里堆规则高。
